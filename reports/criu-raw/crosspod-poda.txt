BUG 1 -- ensure_criu(): the apt index no longer lists criu AT ALL, pinned or
not. `apt-cache madison criu` returned nothing; `apt-get install criu` with
no version also failed ("no installation candidate"); a direct fetch and

    [16:06:48] FATAL: apt-get install criu=4.1.1-1build1 failed

Fix: on apt-get install failure, fetch criu_${CRIU_PKG_VER}_amd64.deb and its

BUG 2 -- abi_check(): false ABI-check failures, two independent causes, same
symptom. First build attempt after Bug 1 was fixed:

    ABI cross-check FAILED -- symbols the plugin needs that /usr/sbin/criu
    does not export:
      __errno_location@GLIBC_2.2.5  atoi@GLIBC_2.2.5  close@GLIBC_2.2.5
      fork@GLIBC_2.2.5  malloc@GLIBC_2.2.5  ptrace@GLIBC_2.2.5  ... (23 total)

  2a. The check only looked at `nm -D` of the criu BINARY. A dlopen()'d
      plugin resolves against the process's whole global symbol table
      (RTLD_DEFAULT) -- criu's own exports PLUS every .so already loaded
      alongside it, libc above all. Every ordinary libc call the plugin
      makes therefore read as "missing". The original hand-built
      environment.txt run only eyeballed the criu-internal names
      (fi_strategy, compel_wait_task, ...) and never hit this; an automated
      diff over the FULL undefined-symbol list does.
  2b. Even after unioning in libc's exports, the same symbols still failed:
      `nm -D` prints an undefined reference as `atoi@GLIBC_2.2.5` (one @)
      but the DEFAULT-version export as `atoi@@GLIBC_2.2.5` (two @s) --
      byte-for-byte these never match.

  Fix: resolvable_exports() now unions `nm -D` of the criu binary with
  `nm -D` of every library `ldd` reports it linked against, and both sides
  of the comparison strip everything from the first `@` before diffing --
  the dynamic linker's own version negotiation at real load time is the
  actual gate; this check only needs to know an object providing the base
  symbol exists somewhere criu will have loaded. Result on the next build:
  "ABI cross-check ok: every undefined symbol in the plugin (34) is
  exported by /usr/sbin/criu or a library it links".

BUG 3 -- fetch_cuda_checkpoint(): the caller does
`CUDA_CKPT_PATH="$(fetch_cuda_checkpoint)"`, capturing ALL of the function's
stdout, but the function's five `say "fetching cuda-checkpoint..."` lines
also go to stdout (say() is a plain `echo`, same as everywhere else in this
script). CUDA_CKPT_PATH ended up holding the whole multi-line status banner
with the real path buried at the end, then got passed as CUDA_CKPT to
criu-matrix.sh and used directly as a command, producing garbage like:

    no cuda-checkpoint at [16:17:10] fetching cuda-checkpoint from
    github.com/NVIDIA/cuda-checkpoint (main, bin/x86_64_Linux) -- needs...
    ...
    VERIFY FAILED: did not find both the plugin-stage-0 success line ...

Fix: redirected every `say` call inside fetch_cuda_checkpoint to stderr
(`>&2`), so only the final `echo "/usr/local/bin/${CUDA_CKPT_NAME}"` reaches
the caller's command substitution. No other function in the script mixes
say() and a return-by-echo the same way (checked: find_cuda_checkpoint,
current_criu_ver, driver_version all either never call say() or don't get
captured), so this fix is scoped to the one function that had the bug.

None of these four bugs are cosmetic: 1 blocked the whole script from
running at all; 2a/2b silently discarded a byte-for-byte correct plugin
build; 3 fed a broken path into the one real proof (--verify) and would
have reported VERIFY FAILED against a plugin that was actually fine.

5. THE A2 WIN VIOLATES ITS OWN ACCOUNTING BOUND -- LOUD FLAG, NOT A RESULT
------------------------------------------------------------------------------
This build's own preload carries 6.14s of imports at a 2.175s mean restore
cost: bound = 6.14 - 2.175 = 3.965s. Measured win was 10.22s -- 6.255s over
the bound, more than double it. Per the hygiene rule this is being said
loudly rather than reported as a win: the 10.22s number is NOT believable
as a measurement of the PVC's effect on cold start, and is not being used
as one.

What the timestamps show (MEASURED): restore stayed tight and did NOT
drift across the whole ~12-minute session -- A1's two restores (54.47s,
53.48s) and A2's two restores (51.38s, 52.20s) all sit within a 3s band,
in fact A2's (later, on the PVC) were the FASTEST of the four. Cold did
drift, and only cold: A1's two colds (58.40s, 56.23s) versus A2's two
colds (59.91s, 64.11s) -- rising, and rising fastest in exactly the window
(16:28-16:33) where `kubectl get pods` shows a new tenant decode pod
(optimized-baseline-nvidia-gpu-vllm-decode-...) starting on the same node,
and node-wide GPU allocation moved from 4/6 to 5/6 (MEASURED, both
`kubectl describe node` snapshots quoted in section 0).

INFERRED, not measured directly (no iostat/per-tenant I/O accounting was
run): a cold boot's dominant phase is weight loading from the shared PVC/HF
cache (environment.txt: ~52% of a TP=1 boot), a multi-GiB read; a restore's
payload is the 0.59 GiB checkpoint image, roughly an order of magnitude
smaller and mostly local page cache by the time it's re-read. A second
tenant's own cold start competing for the same GPFS-backed filesystem would
hit the COLD arm's large weight read hard while barely touching the
RESTORE arm's small image -- which is exactly the asymmetry observed
(restore flat, cold alone rising). This is the most parsimonious
explanation on hand, but it is inference from a coincidence in timing and
a plausible mechanism, not a controlled measurement -- flagged as such and
not folded into the headline numbers.

This is where I got it wrong -- the coordinator called it, correctly, before
section 8 below existed, and the wrong answer is left in above with its
refutation rather than quietly deleted. Short version (full re-examination in
section 8): restore does NOT "barely touch" the weight files. The 0.59 GiB
image is the CHECKPOINT of the import state, not a substitute for the weight
read -- a restored process still execs `vllm serve` and still reads the full
61 GiB from the same GPFS mount cold does. Section 8's restore-3/cold-3 pair,
run back to back on a quiet node, measured IDENTICAL weight-load times
(29.05s, both arms, to the hundredth of a second) -- direct evidence against
the asymmetry this section's mechanism requires.

CONSEQUENCE FOR "does PVC eat the win": the only piece of this comparison
immune to that confound is criu restore latency itself, which stayed tight
throughout: nvme 2.025s mean (n=4 across A1) vs PVC 2.175s mean (n=2 in
A2, but consistent with the two A1-adjacent restores at 1.99s/2.36s showing
no trend) -- a delta of +0.15s, +7.4%, on a ~2s operation. That does not
meaningfully eat a 3-4s win. Applying that delta to A1's own numbers as the
best available estimate: win_PVC (inferred) = imports_carried(6.14s) -
restore_PVC(2.175s) = 3.965s, the same order as A1's directly measured
3.34s. That is an inference from the bound, explicitly not a second
independent cold-control measurement, because A2's own cold arms are
contaminated and cannot supply one in this session.

8.6 VERDICT
------------------------------------------------------------------------------
The coordinator asked explicitly: if the evidence cannot separate the two
hypotheses, say so rather than picking one to be tidy. It cannot, cleanly.
What the evidence supports, plainly:

  * Section 5's SPECIFIC MECHANISM -- "restore barely touches the weight
    read, only cold does the big one" -- is FALSIFIED. 8.4's restore-3/cold-3
    pair shows identical weight-load cost on both arms when conditions match.
    Retracted; left in place above with this refutation per the house
    convention (reports/criu-cuda-checkpoint.txt's NVML section).

  * The coordinator's MECHANISM -- CPU/scheduling contention, not filesystem-
    type asymmetry -- is well-supported structurally (8.3: no static CPU
    Manager pinning on this node, so the 16-core Guaranteed request is a
    quota ceiling, not exclusive cores) and partially supported quantitatively
    (8.4: cold-2's imports phase really was inflated, +30% over baseline).

  * But the coordinator's mechanism, taken as a FULL explanation for the A2
    win violating its bound, does not arithmetically close either: even
    cold-2's own real, inflated imports (8.00s) only raises the bound to
    5.64s against an 11.91s win -- a 6.27s residual that inflated imports
    alone cannot account for. And that residual is not concentrated in
    imports when compared to the clean cold-3 control -- it is spread fairly
    evenly across every phase of the boot (8.4, finding 2), which argues for
    a general contention effect touching the whole process rather than one
    specifically privileging the import phase.

  * A ~4-5s band of unexplained run-to-run variation showed up in restore
    itself (8.5) under conditions this session's instrumentation reads as
    quiet, which neither hypothesis predicts and which this investigation
    cannot attribute to anything specific.

VERDICT: (c), not (a) or (b) as either was originally stated. The direction of
the coordinator's mechanism is right and the specific mechanism in section 5
is wrong and is retracted. But the coordinator's mechanism, quantified
against the one pair where real numbers exist (restore-2/cold-2), explains
roughly a third of the bound violation (imports: +1.86s of a 6.27s residual
after the corrected bound) and leaves most of it unaccounted for, spread
across phases restore also performs identically when uncontended. The honest
statement is: something real and reproducible degraded A2's original cold
arms, it looks like general CPU/scheduling contention rather than filesystem-
type asymmetry (section 5's mechanism is dead), but this investigation cannot
fully quantify it, cannot rule out an additional unidentified contributor,
and turned up a comparable-magnitude noise floor in restore that undercuts
how tightly ANY single pair from n=2 should be trusted on this shared node.
The A2 win of 10.22s/11.91s remains NOT reportable as a PVC-specific result,
now for a better-understood but not fully closed reason than section 5 gave.

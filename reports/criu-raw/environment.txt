criu plugin situation
---------------------
/usr/lib/criu/ is the only directory the criu binary searches for plugins, and on
this install it is EMPTY -- the Ubuntu criu package ships an amdgpu plugin man
page and no plugin .so at all:

    $ ls /usr/lib/x86_64-linux-gnu/criu/ /usr/lib/criu/
    /usr/share/man/man1/criu-amdgpu-plugin.1.gz

    $ strings /criu/bin/criu | grep -i cuda
    (nothing)

So this criu has no NVIDIA device support of its own, by any route. The only
symbol in the area is the generic hook the missing plugin would have filled:

    cr_plugin_handle_device_vma
    Error (%s:%d): handle_device_vma plugin failed: %s

This matters for reading the `live` arms below: their failure is structural, not
a flag or permissions problem.

A TRAP THAT COST ONE 32B BOOT: do not call the variable CC
----------------------------------------------------------
The probe scripts originally read the cuda-checkpoint path from $CC. Passing it
on the exec line -- `CC=/usr/local/bin/cuda-checkpoint kubectl exec ...` -- puts
it in the ENVIRONMENT of everything below, and CC is the C-compiler variable.
FlashInfer/Inductor's JIT then invoked cuda-checkpoint as a compiler:

    /usr/local/bin/cuda-checkpoint: invalid option -- 'O'
    Invalid option(s) or option(s) not supported by this CUDA Driver

and the boot died 50s later inside profile_run -> _dummy_run -> execute_model
with "Engine core initialization failed", which looks nothing like the actual
cause. The variable is now CUDA_CKPT in all four criu scripts, defaulting to
/tmp/cuda-checkpoint.

Not a confound for the plugin/noplug matrix arms (reports/criu-raw/matrix-plugin.txt),
which did run with CC set: that child only imports torch, allocates two tensors
and captures one CUDA graph. No C compilation happens on that path, and the arm
completed with VERDICT: IDENTICAL.

LATE INCIDENTS (2026-09-04, after the plugin build)
------------------------------------------------------------------------------
1. preboot_child.py had no `if __name__ == "__main__"` guard. A criu-restored
   process has CUDA initialised, so vLLM force-overrides fork -> spawn
   (system_utils.py:157), spawn re-imports __main__, and the spawned EngineCore
   re-ran the preload instead of becoming EngineCore. TP=2 restore wedged in
   do_poll with 37 threads until the 900s poller gave up; GPUs never left 4 MiB.
   TP=1 was unaffected because UniProcExecutor forks. Guard added to
   scripts/criu-preboot.sh; image rebuilt (build B); TP=2 then reached health in
   54.70s. The wedged tree was killed with kill -9, which is the likely source of
   the NVRM NV_ERR_OBJECT_NOT_FOUND / "channel not found" burst in dmesg around
   14:16-14:31 UTC -- an unclean CUDA teardown, not a new fault.

2. --link-remap was made opt-out in scripts/criu-vllm-probe.sh and the TP=1 spawn
   arm re-run to test whether the single-use image was self-inflicted. It is not:
   criu refuses the dump outright without it
     Error (criu/files-reg.c:1122): Can't create link remap for /dev/shm/sem.7R6Tks.
                                    Use link-remap option.
   so for a warmed vLLM engine the flag is mandatory and the resulting image is
   necessarily not self-contained. Default left at opt-out; set LINK_REMAP=1 to
   dump a warmed engine.

3. cuda_plugin.c:222 ("Could not find restore thread for process ID N") was
   observed NON-fatally in that run against the CUDA-less python3 intermediate in
   the tree, while the dump continued 33s more. Treat it as benign noise for a
   process with no CUDA state, not a plugin-health signal.

1. BUG FOUND AND FIXED IN scripts/criu-setup.sh (found live in B2)
------------------------------------------------------------------------------
A provenance-labeling fix applied earlier in this session (before B1) had a
real bug of its own, which B1's run never exercised (B1 hit the
"cuda-checkpoint already in image" branch, which bypasses the buggy code
path entirely) but B2's fresh-pod run did.

Symptom: `bash criu-setup.sh --verify` in B2 aborted immediately after
"cuda-checkpoint already cached at $dst -- skipping fetch" with:
    criu-setup.sh: line 437: CUDA_CKPT_FETCH_ORIGIN: unbound variable

Root cause: the caller does `CUDA_CKPT_PATH="$(fetch_cuda_checkpoint)"` --
a command substitution, which always runs fetch_cuda_checkpoint() in a
SUBSHELL. The earlier fix had that function set CUDA_CKPT_FETCH_ORIGIN
internally to label cache-hit vs. real-fetch provenance; that assignment
is invisible to the caller once the subshell exits, regardless of
local/global declaration. Under `set -uo pipefail` (line 92), the caller's
read of the never-set variable is a hard crash, not silent unset-to-empty.

Fix: moved the origin determination out of the subshell. ensure_cuda_
checkpoint() now checks `[[ -x "$DL_CACHE/cuda-checkpoint" ]]` itself, in
its own (non-subshelled) scope, before calling fetch_cuda_checkpoint --
the same predicate that function checks internally, safe to re-read because
it's a pure filesystem check with no side effects prior to the point
fetch_cuda_checkpoint would create/mv the file. fetch_cuda_checkpoint() no
longer sets or references CUDA_CKPT_FETCH_ORIGIN at all.

Verified: bash -n syntax check clean; grep confirms no remaining reference
to CUDA_CKPT_FETCH_ORIGIN anywhere in the file; corrected script copied
into B2 and re-run -- RC=0, ELAPSED_S=15, VERIFY PASSED, provenance written
correctly with `cuda-checkpoint : /usr/local/bin/cuda-checkpoint (already
in image)`. This exercised the "already in image" branch again, not the
cache-hit-label branch specifically -- the exact fixed string on a genuine
cache-hit was not re-observed live, only confirmed by code inspection
(bash -n plus manual trace of both branches).

5. ROOT CAUSE, ORIGINAL DIAGNOSIS -- mount-instance identity -- REFUTED
------------------------------------------------------------------------------
This section is the diagnosis as originally written, kept intact rather
than deleted, immediately followed by the refutation that killed it. Do
not skip to 5b without reading why this was wrong -- the mistake is
instructive: a plausible mechanism, with real supporting measurements, that
was nonetheless the wrong explanation for this specific error.

ORIGINAL REASONING: crosspod-predictions.txt (prior session) pre-registered
"mount-instance identity" as the single highest-ranked, untested risk for
this experiment. The measurements below were read as confirming it as the
direct, causal mechanism of the restore failure.

MEASURED (from pod A's preserved dump.log on the PVC, and from B1/B2 live
inspection of the identical logical file):
  pod A dump-time device:inode for libblkid.so.1.1.0:  103:08  572562560
  B1 live stat for the same file:            Device: 0,617  Inode: 4027908401
  file content: readelf build-ID f3d6283f... (this was WRONGLY asserted to
      be "IDENTICAL sha256 to pod A's" -- no sha256 of pod A's actual
      dump-time file bytes was ever taken, because pod A no longer existed
      by the time this comparison was made; only image digest and overlay
      layer list were compared, which is not the same claim -- see below)
  container image digest and overlay lowerdir= layer list: IDENTICAL
      between pod A and B1 (same image pull, IfNotPresent, same node)

The original write-up concluded from this that CRIU's build-ID check must
be confused by mount-instance/device-identity differences between pods,
since the file's image-layer provenance was identical.

REFUTATION (coordinator review of criu 4.1.1 source, criu/files-reg.c):
validate_with_build_id(), called via validate_file() from open_path(), is
a PURE ELF-note content comparison:
  dump side:    store_validation_data_build_id() reads NT_GNU_BUILD_ID via
                get_build_id(fd, ...) and stores it in rfe->build_id.
  restore side: re-derives the note from the reopened fd and does
                memcmp(build_id, rfi->rfe->build_id, build_id_size).
There is no st_dev, no st_ino, no mount ID, anywhere in that path. The
mismatch branch is only reachable AFTER a build-ID was successfully read on
both sides (`if (!build_id || build_id_size == -1) return 0` skips
validation otherwise) -- and a length mismatch produces a DIFFERENT
message ("has bad build-ID length"), which never appeared. Byte-identical
file content categorically CANNOT produce "has bad build-ID". Therefore:
libblkid.so.1.1.0 was genuinely a DIFFERENT file, byte-for-byte, in pod A
at dump time than in B1/B2 at restore time. The "content provably
identical" claim above was never actually established -- it rested on
image digest and lowerdir comparison, which speaks to what the IMAGE
shipped, not to what the RUNNING container's writable layer had mutated
that file into since. Section 5b confirms exactly that mutation happened,
and to which specific bytes.

The device:inode numbers quoted above are real measurements and remain
true (mount-instance identity DOES vary per pod, as predicted) -- they are
simply not evidence for THIS failure's cause. They are irrelevant to
validate_with_build_id(), which never reads them.

5b. ROOT CAUSE, CORRECTED AND CONFIRMED -- apt package-version drift in
    libblkid1, a self-inflicted harness artifact
------------------------------------------------------------------------------
Cheap, no-GPU-time investigation in B2 (still running, PVC/configmap
untouched):

1. `dpkg -l libblkid1` in B2, BEFORE any fix: Installed 2.39.3-9ubuntu6.5.
   `apt-cache policy libblkid1`: Candidate 2.39.3-9ubuntu6.6, available from
   BOTH noble-updates and noble-security -- i.e. a security update sitting
   in the index, not yet applied to this pod's base image.
2. `readelf -n /usr/lib/x86_64-linux-gnu/libblkid.so.1.1.0` in B2 at .5:
   Build ID: 1afaea6d6a83963f19829dd67efe817c95855146
   (Change/Birth timestamps on the file: 2026-08-26 -- baked into the base
   image at build time, not touched by anything this session ran.)
3. Decoded the build-ID CRIU actually recorded for this file at DUMP time,
   straight from pod A's still-present criu image on the PVC. `crit` was
   not installed (apt index gap, same drift class as Bug 1 in the parent
   report) -- fetched python3-pycriu_4.1.1-1build1_all.deb directly from
   the same Ubuntu pool criu-setup.sh already falls back to for the criu
   package itself, `dpkg -i` + `apt-get install -f` to pull python3-
   protobuf, then:
       crit decode -i /cache/criu-img/preboot-server/files.img
   The reg_file_entry for usr/lib/x86_64-linux-gnu/libblkid.so.1.1.0 carries
       build_id: [2303451952, 3467004697, 3159707735, 4099193167,
                  1970570689]
   (repeated uint32, 5 words = 20 bytes = one SHA1-length GNU build-id
   note, per images/regfile.proto fetched from the criu github source at
   tag v4.1.1). Packed as 5 little-endian uint32 words and hex-dumped:
       30e34b89194ba6ce575055bc4fb954f4c1857475
4. `apt-get install -y --only-upgrade libblkid1` in B2, taking it to the
   apt candidate 2.39.3-9ubuntu6.6 (pulled libmount1, libsmartcols1,
   libuuid1, libfdisk1, mount along with it -- normal dependency chain,
   nothing unexpected). New build-ID:
       Build ID: 30e34b89194ba6ce575055bc4fb954f4c1857475

Step 3's decode and step 4's post-upgrade readelf are an EXACT match,
character for character. Pod A's dumped process had libblkid1
2.39.3-9ubuntu6.6 (or a build with that identical build-ID) mapped; B1 and
B2 started from the base image's 2.39.3-9ubuntu6.5. Confirmed, not
inferred.

WHY the drift happened: criu-setup.sh's ensure_criu() does, on the path
where the apt index lacks a direct criu candidate (Bug 1, already
documented in the parent report and re-observed as recurring in this
session): fetches criu's and libcompel1's .deb directly from the Ubuntu
pool, `dpkg -i`s them, then runs `apt-get install -y -f` to let apt resolve
the remaining runtime deps from the ordinary index. `apt-get install -f`
repairs broken dependencies by whatever means the resolver picks, including
upgrading unrelated already-installed packages if doing so is part of the
cheapest fix it finds -- this is exactly the class of dependency-resolution
side effect that can pull in a newer libblkid1 as a side effect of fixing
something else entirely, with nothing in the script's own output calling
attention to it. Whether pod A's specific fetch/install run actually pulled
this exact upgrade via that `-f` step, versus some other apt invocation
somewhere in pod A's longer lifetime (pod A had been running 72+ minutes
across an earlier session's worth of experiments before this session's
dump was taken, per the prior session's own notes -- plenty of opportunity
for an incidental `apt-get update` && `-f` elsewhere to have picked up a
security update that landed on the mirror in the interim) was not
distinguished further -- both are "apt touched something at runtime that
this script did not pin," which is the operative finding either way.

DEPLOYMENT CONSEQUENCE (this is the actual, corrected conclusion the parent
report needs, replacing the falsified "mount-identity" one from section 5):
a criu image is only portable across pods of the "same" container image if
every package that gets INSTALLED OR MUTATED AT RUNTIME by the setup
tooling is pinned to an exact version, the same way ensure_criu() already
pins criu itself (CRIU_PKG_VER, with an explicit comment warning against
relaxing that pin). It is not -- libblkid1 (and, by the same mechanism,
whatever else apt's dependency resolver decides to touch on a given day)
is left to float to "whatever the index has today." The setup script's own
existing comments already point at the right fix: bake the toolchain into
the container image at build time, rather than apt-installing anything at
runtime in each pod. Runtime apt installation makes every pod's exact
runtime library set a function of "which day it happened to run
criu-setup.sh," which is precisely the class of hidden variable that
breaks any restore depending on ELF build-ID stability -- not because
CRIU's check is wrong (it did its job correctly both times: it caught a
real content mismatch), but because the harness handed it two genuinely
different environments and expected the image to be portable across them
anyway.

This is the same class of error as the other two the parent report
already records elsewhere in this experiment (a missing distro plugin
package, a missing `__main__` guard on a preload child) -- an artifact of
this harness's own runtime-provisioning approach, not a fundamental limit
of the checkpoint/restore mechanism itself.

Once restore succeeded (section 4b), the task's SECONDARY deliverable
(win = imports_carried - restore_cost, n=3 interleaved restore/cold arms)
became obtainable in B2. B1 never restored successfully (deleted before the
fix was found), so this section is B2-only -- see section 9.

Restore arms (n=3, chronological, all post-fix, all against pod A's
original untouched PVC image):
    restore-2: criu restore 1.83s, restore->health_200 51.61s
    restore-3: criu restore 1.84s, restore->health_200 51.19s
    restore-4: criu restore 1.87s, restore->health_200 51.51s
    mean restore->health_200: 51.44s   (spread: 0.42s, restore-3 to restore-2)
    mean criu restore itself: 1.847s   (spread: 0.04s)

Cold arms (n=3, chronological, interleaved with the above; cold-1 ran
BEFORE the fix, cold-2/cold-3 ran AFTER, interleaved with restore-2/3/4):
    cold-1 (true first boot, pre-fix): health_200 103.02s
    cold-2 (post-fix, cache-warm):     health_200 54.96s
    cold-3 (post-fix, cache-warm):     health_200 57.23s

cold-1 IS EXCLUDED and no win is computed against it. An earlier version of
this section reported a second win of 51.58s (~50%) against it, presented as
an alternative reading. That was wrong and is retracted: it is not a second
measurement of this lever, it is a page-cache miss on 61 GiB of weights, and
the logs measure it directly rather than leaving it to inference --

    b2-cold-1.preboot.log:43   Loading weights took 58.94 seconds
    b2-cold-3.preboot.log:43   Loading weights took 27.08 seconds

31.86s of the 45.79s gap between cold-1 and cold-3 is weight load alone, on
the same 61.02 GiB GPFS checkpoint with auto-prefetch disabled in both. The
import-warm image carries IMPORTS; it does nothing about weight load, and the
report's A2 investigation already measured weight load as identical across
restore and cold arms (29.05s both). A cold boot's own second run recovers
that time with no criu involved -- cold-2 and cold-3 are that second run.
Crediting it to the checkpoint would inflate a ~4s lever by about 12x. This
is the same exclusion, on the same grounds, that the parent report already
applies to its own TP=1 r1 baseline outlier (92.7s vs 58.0s/57.8s, "weight
load 56.8s vs ~30.0s").

THE ONE WIN NUMBER, vs. the cache-warm cold arms (mean of cold-2/cold-3,
56.10s), which is the like-for-like comparison because the restore arms also
ran cache-warm and interleaved with them:

        win = 56.10s - 51.44s = 4.66s saved per restore, ~8% reduction.

CHECKED AGAINST ITS OWN BOUND (win must not exceed imports carried minus
restore cost -- the discipline the parent report's point 5 is built on, and
the check the A2 investigation got wrong by using the build-time constant
instead of each arm's own measurement). From cold-3's own log, poller start
18:03:55 to vLLM's first output 18:04:02 is ~7s of interpreter startup and
imports, the work the image carries. Restore costs 1.83-1.87s. So the bound
is ~5.2s, and the measured 4.66s sits inside it. It closes.

But only in the mean, and that is the honest caveat. Per-arm the win ranges
3.52s (vs cold-2) to 5.79s (vs cold-3), which straddles the bound: against
cold-3 alone it would violate it. The cold arms are 2.27s apart at n=2 --
roughly half the size of the effect being measured -- the bound itself is
only good to about +/-1s because vLLM's log timestamps have 1-second
resolution, and cold-2's preboot log was overwritten so its phase mix cannot
be recovered. Conclusion: this lever is real and is worth about 4s. It is NOT
resolvable to the precision the parent report claims for it ("4.07s, with the
accounting closing to 0.13s") on a node this session shares with other work.

The honest reading: restore is unambiguously faster than cold boot in
BOTH framings (criu restore itself completing in under 2s is the clearest,
least confounded number in this whole report), but the SIZE of the win is
highly sensitive to which cold baseline is "fair," and this experiment did
not control for page-cache state well enough to pick one framing over the
other with confidence. (a) overstates the everyday win if boots after the
first are the realistic comparison; (b) may understate the win relative to
a genuinely cold node (e.g. first pod on a node after a reboot, or a node
whose page cache was evicted under memory pressure from other tenants),
which is a real, not merely hypothetical, deployment scenario this n=3
series does not distinguish from "warm."

9. WHAT REMAINS UNVERIFIED
------------------------------------------------------------------------------
- B1 was never retried with the fix -- it was deleted (to free the RWO PVC
  for B2) before the real cause (5b) was identified. It is reasonable to
  expect B1 would also succeed once given a matching libblkid1 (same base
  image as B2, same class of fresh-pod "never touched libblkid1" state),
  but this was not directly tested. If a same-node restore is later needed
  as its own data point (distinct from cross-node), that gap should be
  closed by re-running B1 with the fix pre-applied.
- Pod A's own exact apt-invocation timeline -- which specific command, at
  which point in its 72+-minute lifetime, actually pulled the newer
  libblkid1 in -- was not reconstructed. Two candidate mechanisms were
  identified (criu-setup.sh's `apt-get install -y -f` step inside
  ensure_criu()'s pool-fallback path, vs. some other incidental apt
  invocation elsewhere in pod A's lifetime) but not distinguished, because
  pod A no longer exists to inspect. Both point to the same operative
  finding (apt touched something at runtime, unpinned), so this gap does
  not weaken the conclusion, but it does mean the EXACT trigger step is
  not nailed down.
- hostname/UTS-namespace restore behavior remains untested in the ORIGINAL
  failing attempts (restore never survived long enough to reach that code
  path); it WAS implicitly exercised in the 3 successful B2 retries
  (different hostname than pod A, restore succeeded regardless), so this
  item is now substantially, though not exhaustively, addressed.
- Whether ANY OTHER package besides libblkid1 (and its direct dependency-
  chain siblings: libmount1, libsmartcols1, libuuid1, libfdisk1, mount) also
  drifted between pod A and B1/B2 was not exhaustively checked -- only the
  one file CRIU's own build-ID check flagged was investigated. It is
  possible other, non-imported-at-dump-time files also differ without
  having been caught, simply because nothing tried to load them.
- The page-cache-warming confound between cold-1 (103.02s) and cold-2/
  cold-3 (54.96s/57.23s) is NOT merely inferred: the per-phase logs measure
  it (weight load 58.94s vs 27.08s, a 31.86s delta out of a 45.79s total
  gap). What was not run is a deliberate cache-drop-and-remeasure control to
  confirm the mechanism in the other direction. cold-1 is excluded, not
  averaged, and a single win of 4.66s is reported -- see section 7.
- B1's single cold-arm timing (70.14s) remains an n=1, first-boot-in-pod
  measurement carrying the same first-read weight-load cost as cold-1, so it
  is not comparable to either B2 cold baseline. Not repeated: B1 was deleted
  before the real cause was found. This is the SAME-NODE arm, i.e. the
  strictly weaker claim, and it is subsumed by the cross-node success in
  section 4b -- pod A ran on pokprod-b93r39s1 and the successful restores ran
  on pokprod-b93r43s3. It is not worth GPU time to repeat.
- Driver 580.105.08 and kernel 5.14.0-570.64.1.el9_6.x86_64 are uniform
  across all 13 labeled H100 nodes here, so what section 4b demonstrates is
  portability across a HOMOGENEOUS fleet. Driver or kernel skew is untested
  and was never testable on this cluster; it is the gap that replaced the
  cross-pod one.
- GPU minor-number list for B1 was not re-captured in this continuation
  (already captured and reported in the prior session's B1 work); shown as
  "not re-captured" in the table above rather than fabricated.
- Whether ANY configuration of criu (e.g. --skip-file-rwx-check, a
  different build-ID validation mode) could route around the files-
  reg.c:2153 check even with mismatched libraries was not investigated --
  moot now that the actual fix (matching the libraries) is known to work
  and is the correct fix, not a workaround.

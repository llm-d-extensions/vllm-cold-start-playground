==============================================================================
CRIU + cuda-checkpoint: can pausing/resuming a vLLM process beat a cold boot?
==============================================================================
Setup: Qwen/Qwen3-32B (61 GiB), vLLM 0.28.0, 2 x H100. Two GPU counts tested:
TP=1 (one GPU) and TP=2 (two GPUs). CRIU is a Linux tool that can freeze a
running process to disk and bring it back later; cuda-checkpoint is NVIDIA's
add-on that lets it also handle a process that's using a GPU.
Baseline cold-boot times to compare against: TP=1 58.0s, TP=2 55.0s.

THE HEADLINE

* CRIU cannot touch a GPU process at all without NVIDIA's cuda-checkpoint
  helper and a matching CRIU plugin -- and the plugin wasn't installed by
  default (Ubuntu's package ships no working .so file for it), so it had to
  be built from source. Once that's in place, freezing and resuming a small
  test GPU program works cleanly and byte-identically.
* At TP=1, freezing a fully warmed-up vLLM (weights loaded, ready to serve)
  and resuming it reaches ready in 37.7s vs. the 58.0s cold-boot baseline --
  a genuine 20s / 35% win.
* But that win only works with the "spawn" process-start method, which is
  the exact setting this project normally turns OFF elsewhere to save 15.5s
  on ordinary boots (see the fork-vs-spawn finding in the main README).
  You can have one saving or the other, never both.
* At TP=2, this route doesn't just get slower -- it's blocked outright.
  cuda-checkpoint hangs indefinitely on the worker processes that are
  holding multi-GPU communication state (NCCL), so nothing can even be
  measured.
* A smaller, more useful version of this idea works at both GPU counts:
  freeze a process right after it has finished importing all its Python
  libraries but before it builds the actual engine. That image is tiny
  (0.6 GiB vs. ~76 GiB for a full warm engine), reusable across different
  GPU counts, and saves about 4s at TP=1 and 2.6s at TP=2. This is the
  option worth keeping; everything else here is closed off or not worth its
  cost.
* One more hard rule: freezing a warmed engine requires a CRIU flag
  (--link-remap) that makes the resulting image depend on leftover state on
  the same machine -- so that image can only be restored once, back onto
  the exact pod that produced it. You cannot build one image and reuse it
  on many replicas via this route.

WHY A FULL-ENGINE FREEZE CAN'T WIN AT TP=2, EVEN IN THEORY

At TP=1 the slow part of a cold boot is loading 61 GiB of weights (30s).
At TP=2 the weights are split across 2 GPUs and load faster (13.5s); the
slow part becomes importing Python libraries twice, once per worker (22.6s
of CPU work, no GPU involved). A full-engine freeze/resume replaces "read 61
GiB of weights" with "read a diskimage that also contains weights + KV
cache + captured GPU graphs + the interpreter itself" -- i.e. a BIGGER file
to read, doing the same work, not less. At TP=2 that image roughly doubles
in size while the boot it has to beat gets faster, so the math goes
negative before you even hit the NCCL hang.

Predicted-vs-measured check: a back-of-envelope estimate said TP=1 should
win by about 12s; it actually won by 20s, because reading the image from
disk and copying it to the GPU happen at the same time rather than one
after the other. Good reminder that "add up the pieces" underestimates when
steps can overlap.

WHAT ACTUALLY BLOCKS A FULL-ENGINE FREEZE AT TP=1 (AND HOW IT GOT FIXED)

The first attempts failed with a low-level file-descriptor error. It looked
like NVIDIA's monitoring library (NVML) was the culprit -- a plausible
theory that was directly tested and disproven. The real cause: vLLM's
worker process was started by "forking" (cloning the parent process), which
means it inherited some GPU-related file handles instead of opening its
own, and the freeze tool can't account for handles it didn't see opened.
Switching vLLM's worker start method to "spawn" (a fresh process instead of
a clone) fixed it completely -- confirmed by a clean, fully automatic
freeze-and-resume round trip with byte-identical output.

THE IMPORT-WARM IMAGE (the one worth keeping)

Idea: don't freeze the whole running engine -- freeze a process right after
it has imported PyTorch, vLLM, and the API server code, but before it
builds anything. Restoring that process, then letting it continue on into
`vllm serve`, skips paying for those imports again.

- Image size: 0.59 GiB (vs. 76 GiB for a full warm engine).
- Saves 4.07s at TP=1 (7.4% of the boot) and 2.56s at TP=2 (4.6%), and the
  math checks out closely: the image "carries" about 6.25s of import work
  and costs 2.3s to restore, so ~4s back is exactly what you'd expect --
  there's no more headroom to tune, this is the ceiling for this approach.
- One image works for both TP=1 and TP=2, and it was successfully restored
  three times from the same saved copy -- unlike the full-engine image,
  which can only be used once.
- It still needs the same privileged setup (the CRIU CUDA plugin) as the
  full-engine route, because the one import that earns the 4s -- vLLM's API
  server module -- is also the one that first touches the GPU.
- Cross-pod test (2026-09-08): the same saved image was successfully
  restored on a completely different pod and a different physical machine
  after the original pod was deleted, confirming it's portable -- but only
  if the freeze/resume toolchain is baked into the container image ahead of
  time. An earlier attempt failed 3 times because the toolchain had instead
  been installed live into the running pod, which silently produced a
  slightly different software version each time -- a self-inflicted
  problem, not a real limit.
- Caveat on precision: repeated measurements on a shared machine put the
  saving anywhere from about 3.5s to 4.7s depending on background noise, so
  treat "about 4 seconds" as the honest number rather than any more precise
  figure.
- An earlier, even smaller version of this idea (freezing before importing
  vLLM's API server, so no GPU contact at all and no privileged setup
  needed) looked like it saved 2-3s, but a repeat measurement showed that
  result came from an unusually slow point-of-comparison, not from the
  freeze itself. Its real saving is closer to 0.8s -- not worth building a
  separate pipeline for.

RECOMMENDATION

1. Don't use full-engine freeze/resume for cold start. At TP=1 it is
   genuinely the fastest option measured, but adopting it means giving up
   the fork-based import saving used elsewhere (worth 15.5s on every normal
   boot), needing far more host memory per replica (384 GiB), storing a
   huge single-use image per model, and it doesn't work at all at TP=2.
2. The import-warm image is the one worth keeping: small, reusable across
   GPU counts, portable across pods/nodes (as long as the toolchain is
   baked into the image at build time), worth about 4s. There's no more
   tuning room -- that's the ceiling of what this technique can return.
3. Full-engine freeze/resume is a legitimate option if the goal is "keep an
   already-warm replica in reserve and revive it fast" (warm standby)
   rather than cold start -- but that's a different trade: ~20s saved in
   exchange for ~384 GiB of memory held per parked replica.
4. The one finding that matters even if nobody adopts any of this: the
   fork-based import saving and CRIU freeze/resume cannot be combined. A
   process that's been resumed from a CRIU image always looks like it
   already has a GPU context open, which forces vLLM back to the slower
   "spawn" start method automatically.

Not tested: how this holds up across GPUs with different driver versions
(everything here ran on identical hardware/drivers), whether the full
warm-engine image can ever be made portable, and repeat runs at TP=2 for
the import-warm image (only tested once there).

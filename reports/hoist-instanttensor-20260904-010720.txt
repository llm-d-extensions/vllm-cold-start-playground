VERDICT: the hoist composes with the current loader, and pays more here than the
         projection claimed. Capture phase 11.69s -> 6.88s (-4.81s), time to ready
         37.67s -> 32.23s (-5.44s), steady-state device memory 73.37 GiB in BOTH
         arms (+0.00 GiB). The slowest hoist cycle (33.40s) is still 4.02s faster
         than the fastest base cycle (37.42s), against within-arm spreads of
         1.93s (base) and 2.07s (hoist).

CAVEATS
  * the ready delta (-5.44s) is larger than the capture delta (-4.81s) because
    python imports (10.23 -> 9.67s) and warmup (3.86 -> 3.66s) also came out lower
    in the hoist cycles. Neither phase can be touched by CS_CGSYNC/CS_CGEMPTY, so
    read that ~0.6s as session drift, not as part of the effect.
  * this session's base arm reads 37.67s where runs/lt1-it-* measured 36.87s for
    the same configuration. Node state drifts between sessions; compare arms
    within this matrix, not across matrices.
  * vLLM's own "Graph capturing finished ... took X GiB" reports 2.87 GiB for the
    hoist arm vs 1.84 GiB for base, which reads as "saves the time, not the
    memory". It cannot do otherwise: the delta is measured inside capture_model
    (model_runner.py:871,901), so a free issued after the loop is invisible to it.
    NVML sampled to the end of the run is the number an operator pays, and it is
    identical in both arms.
  * torch._C._host_emptyCache() runs in the same prologue and this probe cannot
    reach it, so the saving remains a lower bound.
  * still not upstreamed, and still TP=1 only: the TP=2 split of this phase has
    never been measured per rank.

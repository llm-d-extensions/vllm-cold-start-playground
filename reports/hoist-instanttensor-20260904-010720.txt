Does the "hoist" CUDA-graph-capture fix (moving a per-capture cleanup step out of the loop so it runs once instead of hundreds of times) still help now that the loader has changed to "instanttensor"?

setup: Qwen3-32B, TP=1 (single GPU), --load-format instanttensor, registry-warm boots. 8 boots total, 4 repeats each of "base" (unpatched) vs "hoist" (patched), first cycle discarded, median of the remaining 3 used.
RESULT: yes, the fix still works, and slightly better than expected — total boot time drops from a 37.67s median to a 32.23s median, a 5.44s improvement.

Why this needed checking: an earlier measurement found this fix saved ~4.0 seconds when using a different loader (fastsafetensors) where weight loading was slower and overall boot was 43.2s. Since then the project switched to a faster loader (instanttensor, weight load down to ~7.7s, boot down to ~36.9s), and this run confirms the same fix still applies on top of the new, faster setup.

Where the savings come from:
- CUDA graph capture time itself: 11.69s -> 6.88s (base vs hoist, averaged over repeats)
- Total boot time: 37.67s -> 32.23s
- GPU memory used once the model is fully running (steady state): unchanged at 73.37 GiB in both versions — the fix saves time, not memory.
- Every "hoist" repeat was still faster than every "base" repeat, even accounting for normal run-to-run variation (about 2 seconds of spread on each side).

Caveats:
- The overall time saved (5.44s) is slightly bigger than the CUDA-graph-capture saving alone (4.81s) because two other steps (Python imports, warmup) also came in a bit faster in the hoist runs — those two steps aren't touched by this fix, so that extra ~0.6s is likely just normal measurement noise, not a real effect of the patch.
- This session's own "base" number (37.67s) is close to but not identical to a similar earlier measurement (36.87s) taken in a different session — node performance drifts slightly day to day, so comparisons should stay within one session's own before/after pair rather than across different sessions' baselines.
- vLLM's own internal memory log reports different numbers for the two versions (2.87 GiB vs 1.84 GiB) for the graph pool — that's an artifact of when it measures, not a real memory cost; the real, GPU-measured number (steady-state, from NVIDIA's own monitoring) is identical in both cases.
- This fix has not been submitted upstream to vLLM yet, and has only been tested on a single GPU — its effect when the model is split across multiple GPUs (TP>1) is still unmeasured.

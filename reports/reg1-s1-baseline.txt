Key takeaways:
- One helper process doesn't start until 49.5s in, so all of its work (imports, GPU setup, weight load) only begins after that point — running engine/worker startup at the same time as API server startup is a straightforward win.
- Imports cost 34.1s total when summed across 5 separate Python processes (worst single process: 14.8s). Only the part actually on the critical path counts toward the total, but this is exactly the cost a pre-warmed or forked process would skip.
- 24.7s of the weight-loading step has no finer breakdown captured (99% of it is one opaque block) — would need more instrumentation to see what's inside it.
- The "which model architecture is this?" check costs 14.4s here because it runs in a throwaway helper process that pays the full cost of importing vLLM (and therefore PyTorch) just to answer a yes/no question. The answer is cached to disk keyed by a hash of the model's code, so the very next boot on the same cache skips it entirely — measured separately at 14.95s cold vs 0.0002s warm. Pre-populating that cache file before this window starts removes the cost from first boot too.
- The CPU limit was hit (container throttled) for 6.76s across 5 periods during startup. Raising the CPU limit would help, since imports, tensor-format conversion, and compilation are all CPU-bound.
- ~198,660 file-existence/listing checks cost 1.74s total — expected overhead on network storage, would be near-free on local disk.
- 1.09s of network calls sit on the critical path (56ms of that is the actual weight download). If the model is already local, turning on offline mode removes the extra metadata round-trips.

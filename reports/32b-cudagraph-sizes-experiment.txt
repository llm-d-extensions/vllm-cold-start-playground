Experiment — cuts the number of pre-built CUDA execution graphs from 51 batch sizes down to 10 (fewer shapes captured at startup means faster boot, but requests of an in-between size run less efficiently later)
run: w6-sizes-c3  |  model: Qwen3-32B, 1 GPU (TP=1), H100

RESULT: ready in 34.3s

Where the time went (largest phases only):
- Loading model weights: 13.6s (40%)
- Python imports: 9.85s (29%)
- Warmup / building CUDA execution graphs: 3.76s (11%)
- Engine startup bookkeeping: 2.65s (8%)
- Capturing CUDA graphs: 2.52s (7%)
- Everything else (API server startup, network lookups, KV-cache sizing, etc.): ~0.85s

Key takeaways:
- Capturing the "PIECEWISE" style of execution graph (used for mixed prefill+decode batches) is far more expensive per graph than the simpler "FULL" style: 10 PIECEWISE graphs took 1.06s to capture versus 161ms for 10 FULL graphs.
- vLLM runs one extra "warm-up" pass before every single graph capture, and this build's runner has no way to turn that off — the setting meant to control it (cudagraph_num_of_warmups) is only read by an older code path.
- The weight-loading call itself (12.3s) has no finer breakdown captured in this trace — would need more instrumentation to see inside it. Same for one part of the warmup step (1.54s, only 8% broken down further).
- The last helper process didn't start until 11.9s in, so its imports/GPU-setup work all happens after that point — running things in parallel instead of sequentially is pure upside.
- Python import time across the 3 processes involved totals 10.0s (worst single one: 7.16s in the main server process).
- The container was throttled on its CPU limit (16 cores) for 6.27s across 4 moments during startup.
- 655ms was spent on network calls (34ms of that the actual weight download, the rest metadata lookups). Disabling Hugging Face's online checks (HF_HUB_OFFLINE=1, TRANSFORMERS_OFFLINE=1) removes these if the model is already stored locally; VLLM_NO_USAGE_STATS=1 also drops one telemetry call.

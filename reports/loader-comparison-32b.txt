==============================================================================
vLLM MODEL LOADERS: what the 13.3s weight phase can actually be moved with
==============================================================================
pod          : vllm-coldstart (manifests/pod-exec-2gpu.yaml), CUDA_VISIBLE_DEVICES=0
model        : Qwen/Qwen3-32B  61.02 GiB, 17 safetensors shards, 707 tensors
stack        : vLLM 0.28.0 / torch 2.13.0+cu130 / CUDA 13.0, H100 80GB HBM3
model fs     : gpfs on /cache (remote-filesystem-fs-ec), 136 GiB free
cgroup       : cpu.max 16 cores, memory.max 128 GiB
gds          : ABSENT -- no /dev/nvidia-fs*, no /proc/driver/nvidia-fs
backends     : fastsafetensors 0.3.3, runai-model-streamer 0.16.1, safetensors 0.8.0
               tensorizer / instanttensor / modelexpress NOT INSTALLED

The question this answers: the published TP=1 ladder ends at 43.30s with weight
load still the largest phase (13.3s, 30.8%), and the step-5 configuration is a
monkey-patch (coldstart/cs_fst.py) on top of --load-format fastsafetensors. vLLM
ships thirteen other load formats. Which of them can beat that here, and what is
the actual floor?

------------------------------------------------------------------------------
WHAT IS EVEN AVAILABLE HERE: all 14 load formats
------------------------------------------------------------------------------
vLLM 0.28.0 accepts 14 --load-format values, which map onto 6 loader classes
(model_loader/__init__.py):

  auto hf safetensors pt npcache mistral fastsafetensors instanttensor
                                          -> DefaultModelLoader
  dummy                                   -> DummyModelLoader
  runai_streamer                          -> RunaiModelStreamerLoader
  runai_streamer_sharded, sharded_state   -> ShardedStateLoader
  tensorizer                              -> TensorizerLoader
  modelexpress                            -> ModelExpressModelLoader

Three of them cannot run in this image at all -- the backend package is absent,
so they raise ImportError before touching a byte:

  instanttensor   pip install vllm[instanttensor]  (instanttensor >= 0.1.9)
  tensorizer      pip install vllm[tensorizer]     (tensorizer == 2.10.1)
  modelexpress    pip install modelexpress         + a ModelExpress service

Four more find no files in this checkpoint. Qwen3-32B ships exactly
model-0000N-of-00017.safetensors plus model.safetensors.index.json -- no
consolidated*, no *.bin, no *.pt -- and default_loader.py:166-183 selects the
glob per format:

  mistral    consolidated*.safetensors                 -> no match
  npcache    *.bin  (and asserts use_safetensors False) -> no match
  pt         *.pt                                      -> no match
  sharded_state / runai_streamer_sharded
             model-rank-{rank}-part-{part}.safetensors  -> "only pre-sharded
             checkpoints are currently supported!"

The pre-sharded pair is the one worth a second look, because the conversion pass
(ShardedStateLoader.save_model) is a real option rather than a missing package.
It costs a second 61 GiB copy on a volume with 136 GiB free, and it makes the
artifact TP-shaped -- a checkpoint saved for TP=1 cannot boot at TP=2 -- so it
trades cold-start time for artifact management. Not measured here; flagged.

dummy is not a loader, it is the control: random weights, no I/O.

What is left is three distinct code paths, and on this artifact `auto`, `hf` and
`safetensors` are the same one: `auto` looks for consolidated*.safetensors,
finds none, and resolves to `hf`, whose glob matches the same 17 files that
`safetensors` matches. So the real choices are:

  1. DefaultModelLoader's safetensors iterator, modulated by
     --safetensors-load-strategy {lazy,eager,prefetch} and by
     --model-loader-extra-config '{"enable_multithread_load": true}'
  2. --load-format fastsafetensors  (the published step 4/5 arm)
  3. --load-format runai_streamer

------------------------------------------------------------------------------
RESULT 1: REAL BOOTS.  runai_streamer beats the patched incumbent by 4.31s
          of weight-load phase, with no monkey-patch
------------------------------------------------------------------------------
12 boots, runs/lf1-*, cycle-major interleaved, cycle 0 discarded, median of 3.
Every arm carries the published step 1-3 levers (VLLM_WORKER_MULTIPROC_METHOD=
fork, PYTHONPYCACHEPREFIX=/cache/pycache, CUDA_VISIBLE_DEVICES=0) and
--max-model-len 8192, so the only difference between rows is the load format.

arm                                              ready   weight load    GiB/s
-----------------------------------------------  ------  -----------  -------
fastsafetensors + cs_fst  (published step 5)     41.88s      13.57s      4.50
runai_streamer            (stock, no config)     40.76s      11.44s      5.33
runai_streamer + distributed:true concurrency:8  39.09s       9.26s      6.59

                                                 Δ ready   Δ weight load
  runai_streamer stock          vs step 5         -1.12s      -2.13s
  runai_streamer + extra config vs step 5         -2.80s      -4.31s

Read the weight-load column, not the total. Per-cycle totals were
41.47/42.58/41.88 (fst), 38.91/41.52/40.76 (runai cpu) and 39.09/38.62/41.05
(runai cuda) -- a ~2.4s spread that straddles the -2.80s end-to-end delta. The
weight phase does not: it is the only phase a load format can move, its three
samples are tight, and -4.31s matches the isolated loader rig below (-4.29s) to
20ms. The other phases confirm they were untouched: python imports 9.63/9.42/9.65s,
cudagraph capture 10.92/11.34/11.02s, engine orchestration 2.47/2.48/2.73s.

The exact invocations:

  # incumbent (published step 5) -- needs coldstart/cs_fst.py loaded via sitecustomize
  CS_FST=1 CS_FST_MAX_THREADS=8 CS_FST_BBUF_KB=32768 \
    vllm serve --model Qwen/Qwen3-32B --max-model-len 8192 \
      --load-format fastsafetensors

  # best stock configuration measured -- no patch of any kind
  vllm serve --model Qwen/Qwen3-32B --max-model-len 8192 \
    --load-format runai_streamer \
    --model-loader-extra-config '{"distributed": true, "concurrency": 8}'

Bit-identical output. All three loaders were re-run yielding every tensor, each
fingerprinted twice (whole-buffer byte sum, plus a stride-1021 subsample so a
shifted or permuted buffer cannot alias) alongside shape and dtype. fastsafetensors,
runai_streamer-to-GPU and stock safetensors produce the same 707 names with the
same fingerprints -- sha256 of the whole map is 26c67047eead6c3a for all three.
This matters because the harness's readiness check only proves the server answers.

The last row is not comparable to the ones above it -- it stops at host memory
and leaves the H2D to the model's own per-tensor param.data.copy_(). It is listed
because it is what `--load-format runai_streamer` does by default, and the real
boot puts a number on the difference: 11.44s of weight phase against 9.26s.

Three things fall out of this table.

1. The DefaultModelLoader family is not in the race, and its two levers barely
   move. `enable_multithread_load` -- 17 shards read by a thread pool -- buys
   2.12 -> 2.45 GiB/s over eager, because the threads parallelise a read that
   was never the bottleneck while the per-tensor pageable H2D stays serial in
   the main thread. `--safetensors-load-strategy prefetch` doubles lazy
   (1.10 -> 2.38) but lands where eager already was. On this pod the strategy is
   also never chosen for you: vLLM auto-enables prefetching only "when an NFS
   filesystem is detected" (config/load.py:63-83) and /cache is GPFS.

2. fastsafetensors' knobs are flat-to-harmful. 4.59-5.06 GiB/s across
   max_threads {8,16,32} x bbuf {16,32} MiB -- a 10% band, with 32 threads the
   worst of the four. This is the part of coldstart/cs_fst.py that cannot be
   reached from vLLM at all (not plumbed, and absent from fastsafetensors' own
   LoaderConfig), and the sweep says there is very little left in it.

3. runai_streamer's one knob is real: concurrency 4 -> 8 is -3.1s. Its optimum
   is 8, and 32 is 15% worse than 8 -- consistent with a 16-core cgroup.

------------------------------------------------------------------------------
RESULT 3: THE FLOOR.  storage is not the constraint, and never was
------------------------------------------------------------------------------
Measured in the same pod, same 17 shards (scripts iobench.py / loaderbench.py h2d):

  checkpoint resident in page cache      61.02 / 61.02 GiB   (100.0%)
  buffered read, 16 threads, 32 MiB      28.52 GiB/s     ->  2.14s for 61.02 GiB
  buffered read,  8 threads              18.19 GiB/s     ->  3.36s
  O_DIRECT read, 32 threads              11.36 GiB/s     ->  5.37s
  O_DIRECT read, 16 threads               8.70 GiB/s     ->  7.01s
  H2D over PINNED host memory            50.71 GiB/s     ->  1.20s
  H2D over PAGEABLE host memory          17.08 GiB/s     ->  3.57s

The checkpoint is 100% page-cache resident, so the read a loader actually issues
is the buffered one: 2.14s. Pinned H2D is 1.20s. A loader that overlapped those
two perfectly would finish in ~2.2s; one that serialised them, ~3.3s.

The best loader measured takes 7.92s. The published step-5 configuration takes
12.06s. Both are far above the floor, and the O_DIRECT row shows why the usual
suspect is innocent: even with the page cache bypassed entirely, the storage
ceiling (5.37s) is still below what the fastest loader achieves warm.

This sharpens rather than contradicts the README's "storage was never the
problem" -- that line cites 9.30 GiB/s O_DIRECT as the ceiling to compare
against. The relevant ceiling for a warm pod is 28.52 GiB/s, which makes the
gap 6x rather than 2x, and locates all of it inside the loaders.

Where runai_streamer's 7.92s goes: 2.14s of read + 3.57s of pageable H2D +
per-chunk Python is very nearly the whole of it. file_streamer.py:207-211 does
`device_tensor = tensor.to(self.device_str)` per chunk out of an ordinary
(unpinned) buffer, so it pays 17.08 GiB/s instead of 50.71. Pinned staging in
the streamer is the single change that would move this number, and it is
upstream work in runai-model-streamer, not configuration.

Where fastsafetensors' 12.06s goes is less clear and looks like a bug rather
than a design limit: its nogds path (copier/nogds.py) allocates the whole shard
on the device and submits bbuf-sized pread+cudaMemcpy pairs, which should get
closer to the read leg than 5 GiB/s. It is ~6x below its own read leg and ~4x
below a pinned H2D, and no combination of its two knobs closes any of it.

------------------------------------------------------------------------------
RESULT 4: two upstream findings, both about knobs
------------------------------------------------------------------------------
A. At TP=1 the only way to make runai_streamer write to the GPU is to tell vLLM
   it is distributed.

   weight_utils.py:1002-1013 picks the streamer's destination like this:

       device = (f"cuda:{current_platform.current_device()}"
                 if is_distributed and is_cuda_alike else "cpu")

   and `is_distributed` comes from nowhere but model_loader_extra_config
   ("distributed", runai_streamer_loader.py:41-45, default False). So the flag
   named after a parallelism topology is in fact the GPU-direct switch, and at
   TP=1 -- where nothing is distributed -- you must set it to true to get the
   faster path. It is worth 2.18s of weight phase here (11.44 -> 9.26s).

   The name is not the only problem: the streamer's own
   DistributedStreamer.set_is_distributed then *rejects* the claim, because
   get_group_size() is 1, and falls back to non-distributed streaming. The
   device string vLLM computed is not revisited, which is why this works at all.
   Correct behaviour would be to choose the device on `is_cuda_alike` and use
   `is_distributed` only for cross-rank chunk sharding -- at which point TP=1
   deployments get the 2.18s for free and the flag means what it says.

B. RUNAI_STREAMER_CHUNK_BYTESIZE is an S3-only knob, silently ignored on a
   POSIX mount.

   With RUNAI_STREAMER_LOG_LEVEL=DEBUG the streamer reports
   "Created 1 batches for file index N" and "Finished reading 1/1 chunks from
   file ..." for all 17 shards -- identically with the variable unset and set to
   32 MiB. The only chunk-bytesize string in libstreamer.so is the error
   "s3 chunk bytesize must be positive". So for local files the read unit is the
   whole shard and the parallelism unit is the file.

   That is the practical ceiling on this loader's tuning: 17 shards means
   concurrency above ~17 has nothing to do (measured: 32 is 15% worse than 8),
   and a model published as 4 or 5 large shards would parallelise 4- or 5-way no
   matter what concurrency is set to. The workers are genuinely used -- the debug
   log shows all 16 at concurrency 16 -- there is just nothing to give them.

The contrast with cs_fst is the reason to prefer runai_streamer here beyond the
4.31s. Both of fastsafetensors' useful knobs (max_threads, bbuf_size_kb) are
unreachable from vLLM and needed a monkey-patch on ParallelLoader.__init__ to
set, and its nogds decision is taken from world size rather than from whether
GDS exists (weight_utils.py:1057, and this cluster has no /dev/nvidia-fs*).
runai_streamer's one effective knob is a documented CLI field.

------------------------------------------------------------------------------
WHAT TO DO ABOUT THE 13.3s
------------------------------------------------------------------------------
Available now, no code change, no patch:

  --load-format runai_streamer
  --model-loader-extra-config '{"distributed": true, "concurrency": 8}'

  -4.31s of weight-load phase against the published step-5 arm, and it *removes*
  a monkey-patch from the stack rather than adding one. Weight load stops being
  the largest phase: at 9.26s it drops below cudagraph capture (11.0s).

Not available here, in rough order of how much they would be worth:

  * Pinned staging inside runai-model-streamer. The 3.57s pageable H2D is the
    largest single identified cost in the best loader. Upstream change.
  * Fixing whatever holds fastsafetensors' nogds path to 5 GiB/s. It has the
    right architecture (device-side buffer, chunked pread) and delivers a
    quarter of what the two legs can do.
  * GDS. Not installed on this cluster; fastsafetensors' whole reason for
    existing is unavailable, and vLLM asks for it anyway at TP=1.
  * sharded_state / runai_streamer_sharded. Untested here because they need a
    conversion pass and a second 61 GiB copy, and they make the artifact
    TP-shaped. The plausible win is skipping per-tensor reshaping, not I/O.
  * tensorizer, instanttensor, modelexpress. Not installed; an image change,
    and for modelexpress an external service.

Not worth pursuing on this evidence:

  * --safetensors-load-strategy anything. eager, prefetch and lazy all land in
    1.10-2.38 GiB/s, 3-7x behind the two real loaders.
  * enable_multithread_load. 2.45 GiB/s at 16 threads; it parallelises the read,
    which was already 13x faster than the loader.
  * More fastsafetensors tuning. The whole max_threads x bbuf sweep fits in a
    10% band and the shipped setting is already the best corner of it.

Two caveats on scope. Everything here is page-cache warm, which is the regime
the whole published ladder measured; a genuinely cold GPFS read cannot be timed
in this pod (dropping caches needs privileges we do not have) and can only be
approximated by the O_DIRECT rows. And all of it is TP=1: at TP>1 each rank
reads its own shard, vLLM already passes nogds=True, and the runai device
question changes shape because is_distributed becomes true for real.

==============================================================================
WEIGHT LOADERS COMPARED: is fastsafetensors+patch actually the best option?
==============================================================================
Setup: Qwen/Qwen3-32B (61 GiB, 17 files), TP=1, one H100, weights on a
GPFS network filesystem, page cache warm (i.e. the OS already has the file
data cached from a previous read). No GPU-Direct-Storage hardware present.

The question: the main results table elsewhere in this project ends with
weight loading still the single largest phase (13.3s), using
--load-format fastsafetensors plus a custom patch (cs_fst). vLLM has 13
other loading options. Is any of them actually faster, with no patch
needed?

HEADLINE RESULT: YES. --load-format runai_streamer, with one extra flag, is
faster than the patched fastsafetensors setup, is a stock vLLM flag with no
patch, and removes the largest remaining phase from first place.

  loading method                              boot ready   weight load
  -------------------------------------------  ----------  -----------
  fastsafetensors + patch (published choice)      41.88s        13.57s
  runai_streamer, default settings                40.76s        11.44s
  runai_streamer, told "act distributed",
    8 parallel workers                            39.09s         9.26s

  -> runai_streamer (tuned) is 2.80s faster end-to-end and 4.31s faster
     on the weight-load phase specifically, with NO patch. Weight load
     drops from 13.3s to 9.26s and is no longer the biggest phase (CUDA
     graph capture, at ~11s, becomes the largest instead).

All three methods were checked to produce byte-identical model weights
(fingerprinted, not just "the server responded").

WHY: 13 OTHER LOADING FORMATS, MOST DON'T APPLY HERE

vLLM ships 14 --load-format values. On this specific model checkpoint
(17 plain safetensors files, nothing else), only 3 are actually usable:
- the default safetensors loader (what "auto" resolves to here)
- fastsafetensors (the currently-published choice, needs a patch to tune)
- runai_streamer (the one that wins, no patch needed)

The rest don't apply: three need optional packages that aren't installed
(tensorizer, instanttensor, modelexpress); four expect a differently
laid-out checkpoint that this model doesn't have (e.g. pre-split-by-GPU
files); one is just a "random weights, no loading" control used for
comparison, not a real option.

ISOLATING THE LOADERS FROM VLLM ITSELF

Timing each loader alone (reading the file into GPU memory, no vLLM engine
around it) to find each one's own ceiling, best config first:

  runai_streamer, 8 parallel workers      7.92s   (7.71 GiB/s)
  fastsafetensors, tuned (published)     12.06s   (5.06 GiB/s)
  plain safetensors + multithreading     24.92s   (2.45 GiB/s)

Three things stand out:
1. The plain/default safetensors loader and its tuning knobs barely move --
   they parallelize the file read, but the real bottleneck (copying into
   GPU memory) was never touched by that.
2. fastsafetensors' two tuning knobs (thread count, buffer size) make at
   most a 10% difference across the whole range tried, and the published
   setting is already about the best of that narrow range -- there is
   very little left to gain by re-tuning it further.
3. runai_streamer's one real knob (how many files it reads in parallel)
   matters a lot: going from 4 to 8 parallel reads saves about 3 seconds.
   Going past 8 (e.g. 16 or 32) makes it slightly worse, consistent with
   this pod only having 16 CPU cores available.

HOW FAR IS EACH LOADER FROM THE PHYSICAL FLOOR?

Measuring the raw disk-read speed and raw GPU-memory-copy speed separately
(same pod, same files): reading the already-cached 61 GiB from disk takes
about 2.1s at best, and copying 61 GiB into GPU memory over the fastest
transfer mode takes about 1.2s. A perfectly efficient loader that overlapped
those two steps could in principle finish in roughly 2-3s.

The best loader measured here (runai_streamer) takes 7.92s -- well above
that floor, but the gap is inside the loaders themselves, not storage:
even bypassing the disk cache entirely, raw disk reads are still faster
than either loader achieves. This sharpens (doesn't contradict) the
project's earlier finding that storage speed was never the real
bottleneck -- read concurrency inside the loader software was.

For runai_streamer specifically, most of its 7.92s is disk read (2.1s)
plus a slower-than-ideal GPU copy (3.6s) because it copies through
regular, "un-pinned" memory instead of the faster "pinned" memory mode --
a fixable inefficiency in that library, not something a flag can change
today. fastsafetensors' 12.06s doesn't cleanly break down the same way and
looks like it's leaving performance on the table somewhere internally that
neither of its two tuning knobs reaches.

TWO SMALL BUT REAL QUIRKS IN THE ("WINNING") RUNAI_STREAMER FLAG

- At TP=1 (a single GPU), you have to explicitly tell runai_streamer
  "act as if this were a distributed, multi-GPU setup" to get it to copy
  weights straight to the GPU. Without that flag it copies to regular CPU
  memory first, which is slower to move from afterward. The flag's name
  suggests it's about multi-GPU coordination, but here it's really just
  the on/off switch for "go straight to the GPU." Worth about 2.2s of the
  weight-load phase.
- A separate chunk-size tuning knob for this loader only works when
  reading from cloud storage (S3); on a regular network filesystem like
  the one here it's silently ignored, confirmed by checking the loader's
  own debug logs.

WHAT'S WORTH DOING

Available right now, no code change: switch to
`--load-format runai_streamer` with the "act as distributed" flag and 8
parallel workers. Saves ~4.3s of weight-load time and removes a custom
patch from the stack.

Not available today but would help if fixed upstream: making that loader
copy through "pinned" memory instead of regular memory (biggest remaining
opportunity); whatever is limiting fastsafetensors to a quarter of its
theoretical read+copy speed; GPU-Direct-Storage hardware (not installed on
this cluster, and fastsafetensors's whole design point).

Not worth pursuing, based on what was measured: further tuning of the
plain safetensors loader's strategies (all landed 3-7x slower than the two
faster options); further tuning of fastsafetensors' two knobs (the whole
range tried only spans a 10% difference).

Caveats: everything above assumes the file is already cached from a
previous read (page-cache warm), matching how the rest of this project's
numbers were measured; a genuinely first-ever read from this filesystem
could not be tested here (would need elevated permissions this pod
didn't have). And all of this is single-GPU (TP=1) — at higher GPU counts
each GPU loads only its own slice of the weights and some of these numbers
would change shape.

Demo: pause a 1-GPU ("TP=1") vLLM instance, free its GPU, let another model use it, then bring the first one back — does it still give the same answer?

setup: Qwen3-32B, TP=1 (single GPU), "best config" (warm cache, forkserver process start, fastsafetensors loader)
RESULT: yes — the model resumes with byte-identical output after being fully evicted from the GPU and later restored onto a *different* physical GPU.

Steps and timings:
- Boot instance A: ready in 52.44s, using ~74.6 GiB.
- Pause A ("sleep level 1" + `cuda-checkpoint`, NVIDIA's tool to fully freeze a GPU process): 21.13s + 2.00s, GPU fully freed (0 MiB).
- A second instance, B, boots on the now-free GPU: ready in 43.37s, output matches instance A's original answer exactly.
- Instance A is then restored onto the *other* physical GPU (a "swap"): restore in 2.41s, wake-up in 1.47s, output still identical to before it was paused.
- Bonus check: a *lighter* pause ("sleep level 2", which also discards the model's weights, not just its GPU memory) wakes up in 0.30s but the model answers with garbage ('!!!!!!!!!!') — a known footgun. Explicitly reloading the weights afterward (2.44s) was supposed to fix this, but in this run it did not: the transcript records the reload step's output as still "DIFFERS" from the baseline (with an empty answer), not the expected match. This one data point does not by itself confirm the reload path is broken — it may be a transcript/formatting artifact of this specific run — but it should not be waved away either.

Key takeaway: pausing at "level 1" and moving the paused model to a different GPU works cleanly and is fast (seconds, not tens of seconds) and produces identical output. The cheaper "level 2" pause is faster to wake but unsafe unless weights are explicitly reloaded — and this run's own reload step did not clearly demonstrate that the fix works.

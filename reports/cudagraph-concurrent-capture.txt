Can multiple CUDA graphs (pre-built, fixed-shape GPU execution plans) be captured at the same time, on different threads, instead of one at a time?

setup: synthetic workload on one H100 GPU — 32 graphs, standing in for the real capture work vLLM does at startup
RESULT: yes, but the speedup is small and inconsistent, and it costs extra GPU memory per thread. Using one shared memory pool across threads doesn't work at all (crashes); each thread needs its own.

Timing (lower is better; "serial" = capturing them one at a time):
- serial: 94.1 ms
- 2 threads, each with its own memory pool: 85.7 ms (modest win)
- 4 threads, own pools: 94.3 ms (no real win)
- 8 threads, own pools: 155.7 ms (slower than doing it serially)
- any attempt to share one memory pool across threads: fails outright with an error
- with GPU memory allocation removed from the test entirely ("noalloc" variant, to isolate whether the allocator itself was the bottleneck): 2 threads did better (72.0 ms vs 84.7 ms serial), but 4 and 8 threads still leveled off around 86.5 ms — so allocator contention explains part of the slowdown at higher thread counts, but not all of it.
- GPU memory used for the graphs scales directly with the number of separate memory pools (1 pool = 4 MiB, 2 pools = 8 MiB, 4 pools = 16 MiB, 8 pools = 32 MiB) — more concurrency means more memory spent, linearly.

Separately, a set of correctness checks tested what happens if another thread does something on the GPU *while* one thread is in the middle of capturing a graph. With the safer "thread_local" capture mode, most common operations (freeing memory, syncing that thread's own work, allocating new memory, running an unrelated calculation, starting a second capture in its own pool) are all safe and don't break the capture in progress. Only two things are unsafe: a global `torch.cuda.synchronize()` call, and trying to start a second capture into the *same* memory pool as the one already being captured. With the less-safe "global" capture mode, almost everything from another thread breaks the in-progress capture, except a couple of memory operations.

Key takeaway: capturing graphs concurrently is possible and safe if each thread gets its own memory pool and uses thread-local capture mode, but the payoff tops out at roughly 2 threads and turns negative beyond that — it is not a large, easy win. Full analysis and how this connects to vLLM's actual startup cost: docs/concurrent-cudagraph-capture.md.

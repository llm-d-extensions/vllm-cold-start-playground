Trace: exactly where does vLLM first create a CUDA context (claim a GPU), and does that happen earlier when running across 2 GPUs (TP=2) than on 1 GPU (TP=1)?

setup: Qwen3-32B config resolution only (no actual model boot), compared at TP=2 and TP=1
RESULT: at TP=2, a CUDA context gets created much earlier than expected — during basic config setup, before the engine itself is even built. At TP=1, this does not happen at all.

What the trace shows (TP=2): building the engine's configuration triggers a check for a specific optimization (`flashinfer_max_size`), which — just to read one constant value — ends up importing the third-party `flashinfer` library. That library's own import-time code needs to know which GPU model it's running on (to name a cache folder), and asking that question is what creates the CUDA context — several seconds before vLLM has even decided how it wants to start its worker processes.

At TP=1, the same code path was checked and the CUDA context was never created during config setup — confirming the difference is specific to running across multiple GPUs.

Why this matters: creating a CUDA context this early forces vLLM to use the slower "spawn" process-start method for its workers instead of the faster "fork" method (fork isn't safe once CUDA is already active in the parent process) — see README.md and docs for how much that costs. The root cause is an import chain: vLLM's config code imports a fusion-optimization module just to read one constant, and that module imports flashinfer, whose own import path happens to touch the GPU.

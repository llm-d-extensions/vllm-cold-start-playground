Demo: same pause-and-move test as the TP=1 version, but with a 2-GPU ("TP=2") instance — does pausing work here too?

setup: Qwen3-32B, TP=2 (tensor parallelism across 2 GPUs), "best config" (warm cache, forkserver process start, fastsafetensors loader)
RESULT: no — pausing (checkpointing) got stuck and the whole run had to be force-killed. The rest of the demo (second tenant, restore, etc.) could not be attempted.

What happened:
- Boot: ready in 95.79s, ~79.5 GiB used on each GPU.
- "Sleep level 1" (park the model, keep its GPU-graph state) worked: 11.36s.
- The detach step meant to release GPU-to-GPU communication state before freezing (`/checkpoint_prepare`) reported success in 0.06s.
- The actual freeze step (`cuda-checkpoint`, NVIDIA's tool to evict a GPU process to 0 MiB) hung indefinitely on the first of the two GPU worker processes — confirmed stuck for over 29 minutes, not just slow. The second worker then hung the same way. A direct wake-up attempt also failed (connection dead after 30s). The whole process tree had to be forcibly killed to recover; afterward both GPUs cleanly returned to 0 MiB, meaning the underlying GPU driver itself was fine — only the vLLM/checkpoint process got stuck.

CORRECTION (added after further investigation, kept alongside the original transcript above):
Two things the original write-up got wrong:
1. It's not a case of the two GPU workers waiting on each other — the same hang happens even touching only one of them.
2. The "detach" step did not actually release the GPU-to-GPU communication state (NCCL) as claimed — it only released a narrower FlashInfer-specific piece, so the 0.06s "success" freed nothing that mattered here.

The real explanation and the full isolation testing are written up in docs/sleep-mode.md. A follow-up, more controlled retry of this same scenario is reports/tp2-park-flashinfer-20260903-130336.txt (also fails, in a bounded way).

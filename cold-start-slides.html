vLLM cold start: time breakdown & improvement

A Qwen3-32B boot on one H100 now reaches ready in 36.87s, down from 90.65s stock. This part shows where that time goes, what's free to fix, what needs an upstream change, and one config change that buys speed by quietly making serving worse.

Part 1 · Methodology & hardware configuration

What "cold start" means here, and on what hardware

t0 is the vLLM process's own exec time, read from /proc/self/stat field 22 combined with /proc/uptime — not when the shell launched it, not when the probe started. Ready is GET /health returning 200. Pod scheduling, image pull and container creation are deliberately excluded: a separate problem, with separate owners, that would add tens of seconds of variance and hide everything happening inside the process.

Hardware & software, both arms

● TP=1 configuration

1× NVIDIA H100 80GB HBM3, node with 224 cores (cgroup limit 16.0), model filesystem GPFS on /cache (remote-filesystem-fs-ec). manifests/pod-exec.yaml, nvidia.com/gpu: "1".

● TP=2 configuration

2× NVIDIA H100 80GB, same node type and filesystem. manifests/pod-exec-2gpu.yaml — byte-identical to the TP=1 manifest apart from nvidia.com/gpu: "2", same pod name, drop-in replacement.

How a number here earns the word "measured"

Median of 3

Every TP=1 ladder/lever step is a median of 3 runs, arms interleaved within each cycle, with a discarded warm-up cycle so cold bytecode and torch.compile misses land on every arm equally.

Five readiness edges

port_open, api_startup_complete, health_200 (the headline number), models_200, first_token — recorded separately because which one you pick changes what "ready" means.

Phases reconcile

The timeline is swept into non-overlapping phases: sum(phases) + unaccounted == total, always. A large unaccounted row means the instrumentation is missing a patch, not that the number is fuzzy.

What's controlled, and what isn't yet: the TP=1 numbers come from median-of-3 harness runs (runs/lad2-*, runs/w6-*), and so do the TP=2 boot numbers — the same seven arms, 3 repeats each, 21 runs (runs/tp2-*, scripts/tp2-ladder.sh), plus a matched pair at --max-model-len 8192 (runs/tp2m8k-*) so capture and weight load compare across TP without a context-length confound. Everything in Part 2 — the sleep-mode baseline, the checkpoint/restore round trip, and the artifact sizes — is still one live-demo sample at TP=2 (pending experiments #3, #5, #6, #7), flagged where it appears.

Part 1 · A constant worth explaining

VLLM_ENABLE_STARTUP_PLAN: a real 0.6s, and a log line that overstates it

Every arm in this deck runs with VLLM_ENABLE_STARTUP_PLAN=1 set, so it never shows up as a row in any ladder — it's a constant, not a step. vLLM saves the result of its memory-profiling pass (the free-memory baseline and the --kv-cache-memory value it computed) to $VLLM_CACHE_ROOT/startup_plan/, keyed by a hardware-plus-config fingerprint. A later boot that matches the fingerprint, with at least as much free GPU memory as recorded, skips profiling.

first boot, this fingerprint2.01skvcache.determine_memory · writes the plan
repeat boot, plan applied1.37ssame call · −0.6s
sample size1 pairQwen2.5-1.5B-Instruct, not a median of 3 · treat 0.6s as an order of magnitude

Why it's a constant, not a lever

It never pays on the first boot of a given fingerprint — that boot is the one writing the plan. Every arm in every ladder in this deck is past its first boot, so it's already helping the baseline in every table; the reductions reported elsewhere would be slightly larger without it.

What the log line gets wrong

On a skipped boot, vLLM logs Memory profiling will be skipped and then calls profile_run() anyway — 2.31s, because that pass also compiles the model for max_num_batched_tokens and vLLM still needs it. What the flag actually skips is the memory_profiling context and profile_cudagraph_memory(), not the forward pass. Reading the log line at face value overstates the saving by roughly 4×. Documentation bug, unfiled.

The first boot is not the second: 14.95s of model registry nobody was counting

registry, cache empty14.95smedian of 5, in-pod, isolated
registry, cache present0.0002sisolated · 10–33ms in a real boot · a hash and a JSON read
first-boot ladder50.0sfrom 93.6s · −43.69s, −47%

Before vLLM resolves a config it needs to know what the model class supports, and it finds out by importing the model module in a throwaway subprocess — _LazyRegisteredModel.inspect_model_cls runs python -m vllm.model_executor.models.registry to bring back a handful of booleans, and that child pays a full import vllm, so a full import torch. The answer is memoised to modelinfos/<module>-<class>.json, keyed on a hash of the model module's bytes — paid once per (vLLM build, model module) per cache volume, then never again. Every other number in this deck was measured with that file already present. They are second-boot numbers, and until this was instrumented they did not say so.

Weight load halves. Capture does not.

−51% is exactly what "each rank reads its own shard" predicts, and it is what weight load delivers. Capture manages only −21%, not the −50% that "each rank captures half a model" would predict — because the per-size launch overhead across 51 sizes × 2 modes does not divide by rank count even though the per-rank forward does. An on-demand-capture design would have to attack that undivided residue.

Both endpoints were re-run at 8192 rather than compared as-found: capture is the one phase that could plausibly depend on context length. It turns out barely to — 8.74s at 8192 vs ~8.7s at 40960 — so the mismatch that prompted the re-run did not change the reading. Re-anchoring the other way, TP=1 at 40960, is impossible on this node: 32B on one H100 leaves 7.92 GiB for KV where 40960 needs 10.0 GiB, so the engine refuses to start (estimated max 32432). That is a capacity limit, not a cold-start one.
Still not measured, and not inferable from these totals: whether the two ranks capture concurrently or serialize against each other. A phase total says what the wall clock paid, not how the two WorkerProcs interleaved inside it — and the −21% is consistent with either. Part 1 · The loader question

Every load format vLLM ships, measured: −5.97s with no patch at all

The adopted 13.7s weight load was written down as a ceiling phase. It is not one. vLLM 0.28.0 accepts 14 --load-format values over 6 loader classes. Five find no matching files in this checkpoint (mistral, npcache, pt, and the two pre-sharded formats want an artifact that does not exist yet), one is a control (dummy), and three were simply not installed — which the first pass recorded as unavailable rather than measured. That leaves six paths that can be attempted here. Five boot. Three are worth a ladder: same script, same pod, same 8192 context, median of 3 with cycle 0 discarded, and the load format is the only variable.

Why it wins: it deletes the leg Part 1 already blamed

Part 1 priced runai_streamer's 7.92s as 2.14s of read plus 3.57s of pageable H2D, and named pinned staging as the fix — upstream work in someone else's repo. instanttensor does not pin the host staging buffer. It removes it: libaio O_DIRECT writes straight into a ring buffer that already lives in HBM, so the read is the whole cost and the PCIe leg leaves the accounting entirely.

That also settles what to configure: nothing. io_uring is the library's first-choice backend and this container's seccomp profile blocks it, so every run above silently fell back to libaio — and libaio at io_depth 512 already lands on the mount's ceiling, so the fallback costs nothing measurable. Concurrency, chunk size and io_depth are flat within noise and only add setup time; copy=False saves nothing. The correct configuration is the empty one, which is why a 61 GiB read at 11.2 GiB/s is a one-line change here rather than a project.

Part 1 · The loader question

The three ruled out on availability, now priced instead of dismissed

The first pass excluded these three because they were not installed, which is a fact about the image rather than a measurement. All three are now installed in an isolated prefix (pip install --no-deps --target /cache/lp, reached per-arm through PYTHONPATH so the base interpreter and every earlier run stay valid) and booted for real. One of the three is the winner on the previous slide. Of the other two, one fails outright on this hardware and one is a slower route to a loader vLLM already ships.

tensorizer — three configurations, three failures

Default config: CUDA OOM at 78.42 GiB

does not run

A 61.02 GiB model on an 80 GiB H100. vLLM builds the module on the meta device (tensorizer.py:518-527) and then constructs TensorDeserializer with lazy_load defaulting to False, so all 773 tensors are materialized before load_into_module runs. Peak is ~1.3× the checkpoint.

num_readers: 1: OOM at 78.78 GiB

not read buffers

Worth running because it falsifies the obvious explanation. Shrinking the reader pool to one does not help — it makes it marginally worse. The overhead is the eager state dict, not I/O staging.

The lazy_load escape hatch is a TypeError

vLLM bug

{"deserialization_kwargs": {"lazy_load": true}} is the documented way out. It raises TensorDeserializer() got multiple values for keyword argument 'lazy_load' from tensorizer.py:608 (is_vllm_tensorized), which hardcodes lazy_load=True in its own call and so collides with the user's. The only way to make tensorizer fit in HBM is unreachable. Filed nowhere.

And it is not free even when it works

cost before boot

Unlike every other format here, tensorizer needs a conversion pass: 133s of wall clock and a permanent second copy of the weights (773 tensors, 61.03 GiB, all bf16, verified sound) that is specific to (model, vLLM build, dtype, TP). That is a cache-key dimension and a doubled PVC, bought before the first boot is measured.

modelexpress, what this environment lacks, and what nobody upstream owns

modelexpress bare: +47.7s, a slower route to auto

worse

Its LoadStrategyChain tiers [rdma, model_streamer, gds, default] and logs its way down all four: no MX server configured, MX_MODEL_URI not set, GDS not available → Eligible loaders: ['default'] → load_via_native, which sets load_format="auto". A 61.8s weight-load phase — 0.99 GiB/s, an eleventh of what the same pod does with instanttensor — and ready at 90.5s against the adopted config's 42.85s in the same ladder. With MX_MODEL_URI set it reaches its runai tier: ready 39.0s, weight 11.2s, which ties on readiness and loses 1.6s of weight load to calling runai_streamer directly. To beat that it needs a peer service this cluster does not run. Single runs (runs/lf2-mx-c0, lf2-mxms-c0), not medians — the gap is far too large for that to matter, and it did not earn a ladder.

Independent corroboration of the distributed finding

✓ confirms Part 1

modelexpress' runai wrapper defaults MX_MS_DISTRIBUTED=1 and so always sets extra_config["distributed"] = True — an outside project working around the same vLLM quirk this repo found independently: at TP=1 that flag is the only way to make runai_streamer write to the GPU at all.

GPUDirect Storage: absent

no hardware path

No /dev/nvidia-fs* on this node, so GDS cannot be measured here at all — and vLLM still asks for it at TP=1 and pays a failed probe (see the upstream slide). NIXL is present; GDS is not.

io_uring: blocked by seccomp

container policy

instanttensor's preferred backend rejects itself as not available on this system inside this container. It costs nothing here because libaio already saturates the mount, but on faster storage this is a cluster-policy decision that would cap the loader.

sharded_state / runai_streamer_sharded

still untested

Both need a pre-sharded artifact written per TP degree — the same conversion-pass and cache-key tax as tensorizer, without tensorizer's failure mode. Not measured; the honest reason is that nothing above leaves enough of the phase to be worth the artifact.

The upstream RFC is thinner than the idea

no maintainer response

vllm#36091 is closed with zero comments, no maintainer reply and no linked PR. It benchmarks only against plain safetensors (57.4s → 1.77s, 39 GB/s on 1×H20) while dismissing fastsafetensors and runai in prose, discloses no limitations, and never explains TP sharding. Its 39 GB/s is a statement about its storage, not its loader. The head-to-head on the previous slide is the one the RFC does not contain — which is also the argument for adopting it with eyes open rather than on the RFC's word.

Part 1 · The question that turned that up

Concurrent capture: legal, bit-exact, and worth ~0.5s

The captures run one after another in a for loop, ~7.1s of the phase is pure CPU with the GPU near idle, and the container has 16 cores and uses one. PyTorch says concurrent capture is forbidden — graphs.py:419, "only one capture may be underway at a time in the process." That comment is wrong, and the string that backs it belongs to an allocator backend this build doesn't use.

✓ It works

maxdiff = 0 on every graph in every threaded arm — same kernels, same arguments. Overlap of 2.00/2.00 says the captures really were in flight simultaneously, not politely queueing. Needs capture_error_mode="thread_local" and one mempool per thread.

⚠ The ceiling is two threads

Three independent invocations: 2 threads 1.10–1.21×, 4 threads 0.99–1.05×, 8 threads 0.60–0.64× — slower than serial while achieving 7.57× overlap. Not the GIL (cpu/wall 3.47) and not the caching allocator (pre-warmed-pool controls behave the same): it is the driver's own per-process capture serialization.

✗ It is not free

+1.08 GiB of GPU memory per extra mempool at 32B — exact, linear, and confirmed by two independent accountings. On the v2 runner that memory is unbudgeted: profile_cudagraph_memory() returns 0, so the failure mode is a late OOM rather than a smaller KV cache.

Part 1 · The solution space

What each option spends to get its seconds back

Three phases dominate TP=1 boot time: weight load, CUDA graph capture, python imports. Sorted below by what each fix spends, not by how many seconds it saves. Weight load is the closed one: the instanttensor load format takes it to within 1.5s of pure overhead, for free. Capture and imports are what is left.

The real answer — not ours to ship engineering inside vLLM

Hoist torch's per-capture prologue out of the capture loop — −4.0s end to end, at no memory cost, the cheapest thing on this slide and a prerequisite for the rest of it. Then: capture on demand (11.4s off readiness, 3.3s deleted), a cheaper PIECEWISE forward (4.6× residual gap once the prologue is accounted for), overlapping capture across sizes (no longer unquantified: ~0.5s, bit-exact, +1.08 GiB per thread), or honoring cudagraph_num_of_warmups on the v2 runner (2.19s, dead knob). Detail on the two capture slides above.

Evaluated and closed dead end

Foundry (persist graphs to disk): worth evaluating, but external and driver-welded, numbers unverified on this hardware. Serializing the cuda-checkpoint snapshot for a future boot: impossible, not merely unimplemented — CUDA exposes 95 cuGraph* symbols and none produce or consume bytes.

Part 1 · Upstream status

What is patched here, and what should be upstreamed

Three of the four adopted wins are configuration — nothing patched. Everything below this line is either a monkey-patch standing in for a real fix, a proposal that doesn't exist in vLLM yet, or a bug filed nowhere.

Process model — fork / forkserver

forkserver is rejected by vLLM itself

blocked

envs.py:930 declares choices=["spawn","fork"]; get_mp_context() (system_utils.py:168) raises ValueError on any other value. vLLM already contains forkserver support (api_server.py:111-117) — it just isn't reachable.

forkserver preloads the wrong module

bug

api_server.py:116 preloads vllm.v1.engine.async_llm (the frontend) instead of what actually gets forked (EngineCoreProc) — 23 modules re-imported per worker, worse at TP>1.

fork-safety check can be wrong

bug

_maybe_force_spawn tests torch.cuda.is_initialized(), which can read False while fork is already broken — the tilelang counterexample.

fork itself is borrowed time

fragile

vLLM silently reverts to spawn if CUDA is already initialized in the parent, and Python 3.14 moves the Linux default to forkserver outright.

Storage path — load formats, fastsafetensors, GDS

nogds keyed on world size, not on GDS availability

bug

weight_utils.py:1057: nogds = pg.size() > 1. At TP=1 vLLM always asks for GPUDirect Storage without checking it exists — costs ~1.7-2.6s of failed probe, silently, every boot.

max_threads / bbuf_size_kb unreachable

not plumbed

Not exposed by vLLM's CLI, and absent from fastsafetensors' own LoaderConfig. The monkey-patch here (coldstart/cs_fst.py) is the only way to set them at all.

tensorizer's only escape hatch is a TypeError

bug, unfiled

vLLM builds the module on meta and then lets TensorDeserializer default to lazy_load=False, so all 773 tensors are materialized before load_into_module — ~1.3× the checkpoint, which OOMs a 61 GiB model on an 80 GiB H100. Passing deserialization_kwargs.lazy_load is the documented fix and it raises multiple values for keyword argument 'lazy_load', because is_vllm_tensorized (tensorizer.py:608) already hardcodes it. The format is unusable on this hardware and the workaround is unreachable.

runai_streamer: distributed doubles as device selection

bug

At TP=1 the only way to make runai_streamer write to the GPU instead of host RAM is to set {"distributed": true} on a single-rank job — a flag whose name says nothing about devices, defaulting to False (runai_streamer_loader.py:41-45). Independently corroborated from outside: modelexpress' runai wrapper defaults MX_MS_DISTRIBUTED=1 and sets it unconditionally. Its sibling RUNAI_STREAMER_CHUNK_BYTESIZE is silently S3-only and does nothing on a filesystem path.

The fastest load format has no upstream owner

✓ measured, no maintainer

--load-format instanttensor is the best result in this repo's loader work (−5.97s, no patch), but vllm#36091 is closed with zero comments and no PR, and vLLM's own plumbing hedges it: weight_utils.py:1121-1124 passes process_group only when world_size > 1, so TP=1 silently runs it in non-distributed mode, and copy=True is hardcoded. Adopting it is a supply-chain judgement call, not a tuning decision — and the numbers to make that call are on the loader slides rather than in the RFC.

Warmup & capture

torch's capture prologue runs 3366 times

✓ measured, precise ask

torch.cuda.graph.__enter__ (torch/cuda/graphs.py:437 in this build) device-syncs and calls empty_cache() before every capture, and vLLM builds 3366 of them. Moving both to one call after capture_model is −4.18s at +0.00 GiB, and it is a prerequisite for concurrent capture rather than a competitor to it. Whether the fix belongs in torch (make the prologue optional) or vLLM (stop using the context manager for bulk capture) is the open question. Not filed yet.

v2's graph-pool memory is unbudgeted

bug

profile_cudagraph_memory() is real on the legacy v1 runner and return 0 on v2 (model_runner.py:843, called from gpu_worker.py:532), so graph-pool growth is invisible to KV-cache sizing — the failure mode is a late OOM, not a smaller cache. Latent today at one pool; load-bearing the moment anyone adds a second (concurrent capture needs one per thread).

On-demand CUDA graph capture

proposal only

80% of the mechanism already exists, but blocked by a silent-corruption bug (capture branch returns uncomputed output) and FULL mode has no lazy dispatch path at all. TP>1 coordination is unverified.

cudagraph_num_of_warmups is dead

bug

Read only by the legacy v1 runner; this build's v2 runner ignores it and runs 102 unconditional eager forwards — 2.19s. Foundry independently hit the same wall and works around it by pinning the v1 runner.

tilelang JIT hook has no off switch

bug

Imports tilelang + TVM (incl. a mobile-GPU backend) to install a hook with nothing to watch if tilelang was never imported — 1.00s cold, 436ms even with warm bytecode.

Architecture check behind an import

easy fix

kimi_k3_triton_warmup imports deepseek_v4 + compressed_tensors purely to reach an isinstance check that returns None for Qwen3 — 417ms.

Outside vLLM entirely

Foundry is a fork, not upstream

external

foundry-org/vllm (branch foundry) and foundry-org/sglang. TP is 🚧 in progress on both engines — "the single biggest gap." Numbers are Foundry's own, unverified on this hardware.

The transferable finding is the trade, not the 20s: Part 1 turns fork on to save 15.5s of worker re-imports on every ordinary boot. A criu-restored process already has CUDA initialized, so vLLM force-overrides it back to spawn — the same veto TP=2 hits on the fork slide, arriving from the opposite direction. ⚠ Single-use as produced

Dumping a warmed engine needs --link-remap for a /dev/shm semaphore vLLM unlinks while still mapped — criu refuses the dump without it. That flag couples the image to state left behind at dump time, so restoring the same image twice fails in 0.19s. Removing the flag doesn't turn this into a tuning knob — criu just refuses the dump outright instead.

✗ TP=2 is closed, not slow

Root and EngineCore, holding no NCCL state, checkpoint in 0.05–0.09s. Both TP workers hang >120s on do_poll — the same NCCL/graph mutual exclusion the previous slide found inside vLLM's own /sleep, now one layer lower, inside cuda-checkpoint itself. Also: 384Gi of host RAM per pod — GPU memory becomes RSS roughly 1:1, and TP=2 would need ~144 GiB before criu writes a byte.

The prize and the price are the same import. Isolating the four modules one at a time: vllm.entrypoints.openai.api_server alone is +3.50s and takes /dev/nvidia* fds from 0 to 11 — that's the whole cost, and it's also what reaches CUDA at all. The other three modules this stage adds (vllm.entrypoints.cli.main, AsyncEngineArgs, uvicorn/fastapi) cost +0.00s; they're already pulled in by that one. There's no cheaper subset to prefetch — the same import that lifts the win from ~0.8s to 4.1s is the one that drags in cuda_plugin.so, cuda-checkpoint, and a privileged pod.
Reusable where the full-engine image was not — and, as of 2026-09-08, shown portable across pods and nodes

One dump, three restores, two topologies

✓ reusable

No /dev/shm coupling — this dump happens before the engine exists, so the full-engine route's --link-remap problem doesn't arise. The same 0.59 GiB image served TP=1 twice and TP=2 once from one build, zero rebuilds, topology chosen after restore.

Cross-pod, cross-node: 3/3, after fixing our own bug

✓ portable

Image rebuilt onto a shared PVC (+0.15s, +7.4% vs node-local nvme), producer pod deleted, a fresh pod on a different node restored it 3/3, correct output every time. First three attempts failed hard on a libblkid.so build-ID mismatch — not a mount-identity limit, criu's build-ID check is a pure content compare that never looks at st_dev/st_ino. The real cause: this repo's own setup script apt-installs the toolchain at pod runtime, and apt pulled libblkid1 forward in one pod's writable layer while the other, hitting a cache, stayed behind — same image digest, different library on disk. Matching versions reproduced the exact build-ID and restore succeeded 3/3. scripts/criu-setup.sh.

Quote the win as ~4s, not to three figures

precision limit

4.07s here and 4.45s in the cross-pod session are the same effect measured twice, but the run-to-run spread on a shared node (0.42–2.27s) is comparable to the effect itself. Per-arm it straddles its own bound rather than closing exactly — one arm lands 0.64s over, attributed to 1-second log-timestamp resolution.

Driver/kernel skew: untestable here

gap

Every node behind this test ran the same driver and kernel, so cross-pod portability is shown only across a homogeneous fleet. A heterogeneous one is the gap that replaced the original single-node question. Also open: whether the 76 GiB full-engine image is portable at all (a different blocker than build-ID), and TP=2 --stage server beyond n=1.

Recommendation: do not adopt the full-engine checkpoint for cold start — not because it's slow, but because of what keeping it costs (give up fork's 15.5s, 384Gi RAM/replica, 76 GiB/model-and-flag combination, single-use images, TP>1 closed outright). Do adopt the import-warm image at --stage server, with eyes open about its ceiling: the win is exactly (imports carried) minus (restore cost), already sitting at that bound — growing it means carrying the next import, which is engine construction, i.e. recommendation one's route and all its costs. If a checkpoint is wanted for warm standby rather than cold start, the TP=1 full-engine result is real and priceable as a different product: 384Gi resident per parked replica, ~20s saved. At TP=2, the same fork veto seen on the standalone TP=2 slide fires inside the launcher too: once CUDA is initialized in the parent, vLLM overrides VLLM_WORKER_MULTIPROC_METHOD back to spawn — system_utils.py:157, "Reasons: CUDA is initialized." So what is a permanent launcher actually for? Not per-boot latency — a standalone process with a warm bytecode cache already imports cheaply, so fork inheritance only claws back what little is left. The real case is operational: the launcher is a resident process that owns instance lifecycle (create / health / delete), amortizes its own ~16s warm-import boot to zero across every subsequent launch, and gives every launch a shared, already-warm cache for free — the model registry, torch.compile artifacts, and the node's page cache all carry over between launches the way they never do between separate standalone processes.

Part 2 · Upstream status

What's not upstreamed yet, Kubernetes side

PyNcclCommunicator has no stable-VA detach

TP=2 · blocked

Parking a TP>1 engine to 0 MiB requires releasing live NCCL/symmetric-memory state, which requires destroying the captured CUDA graphs first — the thing sleep level 1 exists to keep. FlashInfer already ships the stable-VA detach this needs (allreduce.py:204); extending it to PyNcclCommunicator, or making checkpoint_prepare fail loudly instead of reporting false success, is the upstream ask. Not filed yet.

reload_weights crashes the engine

bug

Wiring up vLLM's own Worker.reload_weights() after a level-2 wake doesn't fix the footgun — it crashes EngineCore: NotImplementedError on a Meta-device tensor → EngineDeadError.

Level-2 wake is a silent footgun by design

unguarded

/wake_up returns HTTP 200 in 0.248s and the model then emits '!!!!!!!!!!'. Needs an upstream guard, or a complete "reset the worker" wake path — not just a weight refill.

Device-plugin isolation has no hot-detach

orchestration gap

nvidia.com/gpu: "1" owns the device for the pod's lifetime no matter what nvidia-smi says. Needs MIG, time-slicing, or a hot-detach-capable device plugin — not a CUDA fix.

Cross-GPU migration discards device-plugin accounting

real trade

--device-map restore requires the pod to see every candidate GPU up front, which makes the scheduler's per-GPU accounting fiction. Untested at TP>1, and moot until the stable-VA-detach trade above resolves.

A snapshot format exists after all — only from a privileged pod

tried, still closed here

cuda-checkpoint's own interface is pid-keyed with no output path. CRIU plus a CUDA plugin built from source does write an image to disk — but only from a dedicated, CAP_SYS_ADMIN pod, which neither pod-exec.yaml nor pod-serve.yaml is. Two slides on what that buys and what it costs.

/dev/shm 64 MiB default

landmine

Kubernetes' default emptyDir size is a classic silent TP>1 startup stall for vLLM's multiproc executor. This repo sets 16 GiB explicitly; nothing upstream warns you to.

Closing

What's measured, what's real, and what's next

Current best on one H100, TP=1: 90.65s → 36.87s (−59%), instanttensor load format, no patch, warm model-registry cache. Every phase in that 36.87s is accounted for, including the 14.95s registry subprocess. On two H100s, TP=2: 94.7s → 53.52s (−43%), same load format, phases broken down across 21 runs. Weight load is the phase that moved: a matched ladder across the three working load formats (of vLLM's nine) takes it from 13.69s to 7.70s — −5.97s, no configuration and no second copy of the weights — and adopting it also retires the one monkey-patch the deck previously depended on. TP=2 is still a single live sample in Part 2, where one finding won't move with more measurement: parking to 0 MiB and keeping the captured CUDA graphs are mutually exclusive on this stack. That is now a specific upstream ask, not a "deadlock" label.
